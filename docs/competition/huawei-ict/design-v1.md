# 第十一届华为 ICT 大赛创新赛作品设计方案

## 项目名称

**灵小禅——基于华为 AgentArts 的可信文旅决策智能体**

- 参赛赛事：第十一届华为 ICT 大赛（2026—2027）
- 参赛赛道：创新赛
- 选择赛题：赛题二——基于华为 AgentArts 智能体开发平台的 Agent 设计和应用
- 项目版本：设计方案 V1.0
- 项目基础：灵小禅·灵山胜境 AI 导览系统
- 当前阶段：既有系统基础上的参赛方案设计与技术验证
- 参赛资格状态：待赛事组织方确认既有 AIC 获奖作品的参赛资格及改进要求

## 一、项目摘要

随着生成式人工智能和智能体技术的发展，传统景区导览系统正在从景点信息查询向个性化行程规划和智能决策演进。然而，通用大语言模型虽然具备较强的自然语言理解能力，却难以独立保证复杂旅游路线的物理可行性、时间预算合理性、无障碍通行约束以及景区信息的真实性。

针对上述问题，本项目拟基于华为 AgentArts 智能体开发平台，对现有灵小禅 AI 导览系统进行实质性技术升级，构建融合自然语言理解、混合检索、确定性路线规划、独立约束校验和执行过程审计的可信文旅决策智能体。

项目将充分复用现有系统的工程基础，包括 React 前端、Express/TypeScript 后端、Python 向量检索服务、三路混合检索、场景状态提取、路线规划器及可审计执行记录。在此基础上，将现有业务能力封装为可调用工具，由 AgentArts 负责智能体工作流编排、任务分支控制、工具调用及结果整合。

系统面向普通游客、老年游客、行动不便游客以及具有明确时间限制的游客，支持景区事实问答、复杂需求解析、个性化路线规划、缺失条件主动追问、不可行路线识别和替代方案生成。

项目的核心目标不是让大语言模型直接生成旅游路线，而是构建一种**以智能体完成任务编排、以确定性算法保证约束、以证据链支撑结果解释的可信决策系统**，提升景区导览智能体在复杂真实场景下的可靠性、可解释性和可复现性。

## 二、项目背景与需求分析

### 2.1 现有景区导览系统的主要问题

**（1）事实问答与实际行动脱节。**

传统景区问答系统主要回答景点介绍、开放时间和文化知识等问题，难以将游客的时间预算、当前位置、同行人员、行动能力和游览偏好统一转化为可执行的行程。

**（2）大语言模型缺乏物理约束保证。**

大语言模型能够生成自然流畅的路线建议，但不能仅凭生成结果证明景点之间存在可通行道路，也不能保证总耗时、演出时间窗和返程要求同时满足。

**（3）复杂需求缺乏主动澄清机制。**

游客可能没有提供准确的出发位置、剩余游览时间或行动能力。若系统直接猜测缺失信息，容易形成与真实需求不一致的建议。

**（4）决策过程缺乏可审计性。**

一般问答系统往往只展示最终答案，无法充分解释答案依据、路线选择原因、被拒绝条件以及系统在执行过程中调用了哪些工具。

### 2.2 目标用户

- 普通游客：希望快速了解景点并获得合理的游览安排。
- 老年游客及行动不便游客：需要考虑通行限制、体力负担和合理的休息时间。
- 时间受限游客：需要在有限时间内协调必去景点、演出安排和返程要求。
- 景区运营人员：需要维护知识资料、检查系统运行情况并分析游客反馈。

### 2.3 典型应用场景

游客提出：

“我带行动不便的家人从南门进入景区，只有 90 分钟，希望参观灵山梵宫。如果时间不够，请告诉我应该怎么调整。”

系统应完成以下任务：

1. 从自然语言中提取出发位置、剩余时间、同行人员、行动能力和必去景点。
2. 判断必要信息是否完整，必要时主动追问。
3. 检索景点资料、登记道路信息及相关限制。
4. 调用路线规划工具生成候选行程。
5. 使用独立约束校验器检查连通性、时间预算和行动能力限制。
6. 如果原始要求不可行，说明具体原因，并提供经过重新校验的替代方案。
7. 返回路线、时间安排、证据来源及可行性状态。

需要说明的是，系统输出的路线可行性仅针对已登记并经过验证的数据成立；未核验的道路、步行时间和设施信息必须明确标注，不得将其等同于实时导航保证。

## 三、项目建设目标

### 3.1 总体目标

基于现有灵小禅系统和华为 AgentArts 平台，建设具备任务理解、工具调用、约束验证、异常处理及结果审计能力的可信文旅决策智能体，并通过独立实验验证其实际效果。

### 3.2 具体目标

**目标一：完成 AgentArts 核心集成。**

建立 AgentArts 工作流与现有业务后端之间的标准化接口，使平台能够真实调用场景解析、知识检索、路线规划及结果校验工具。

**目标二：实现复杂游客需求处理。**

支持多条件输入、必要信息追问、路线不可行识别和替代方案生成，避免只提供表面合理但无法执行的建议。

**目标三：强化决策可信度。**

将自然语言生成与确定性规划解耦，确保最终路线必须通过独立校验后才能作为可行方案返回。

**目标四：建立可复现评测体系。**

在固定测试集上比较原系统与 AgentArts 改造版本，评估事实正确性、路线约束违规情况、任务完成情况、工具调用成功率和响应延迟。

**目标五：形成完整参赛交付物。**

完成可运行的软件系统、部署文档、测试数据、实验报告、演示视频和答辩材料。

## 四、总体技术架构

### 4.1 系统架构

系统拟采用分层架构：

1. 用户交互层：负责游客需求输入、路线展示、问答结果及证据呈现。
2. 智能体编排层：基于华为 AgentArts 实现工作流、任务分支、工具调用和结果整合。
3. 知识检索层：复用现有向量、结构化字段和关键词检索能力。
4. 确定性决策层：执行路线搜索、时间预算计算、约束校验和替代方案生成。
5. 数据与审计层：维护知识资料、路网资产、评测数据和执行记录。

总体流程如下：

```text
游客自然语言需求
        |
        v
华为 AgentArts 智能体
        |
        v
需求解析与场景状态提取
        |
        v
必要字段检查与主动澄清
        |
        v
+--------------------------+
|          工具层          |
|                          |
|  知识检索 Tool            |
|  路线规划 Tool            |
|  独立约束校验 Tool        |
|  替代方案生成 Tool        |
+--------------------------+
        |
        v
决策结果检查与异常处理
        |
        v
可行路线 / 主动追问 /
不可行原因与替代方案
        |
        v
证据、约束检查结果与执行记录
```

AgentArts 的工作流和工具调用能力可用于实现上述编排。现有业务服务仍负责其擅长的检索、规划和验证任务，避免将复杂的物理约束计算完全交给大语言模型。

### 4.2 现有系统基础

现有项目已经具备以下工程基础：

- React 前端与 Express/TypeScript 主服务。
- Python 向量检索服务及 ChromaDB 检索基础。
- 向量、结构化和关键词三路混合检索，并采用 RRF 进行候选融合。
- 自然语言场景状态提取及关键字段缺失识别。
- 基于登记路网、时间预算及约束条件的路线规划与验证。
- 问答证据、执行 Trace 和历史评测记录。
- 既有接口包括问答、路线规划、认证及知识库维护等。

现有路线资产记录为 23 个节点和 30 条道路边。该数据规模是当前仓库的记录值，不代表全部道路均已经过现场测绘。

既有评测记录中，历史 50 题事实契约基线为 48/50，即 96.0%；历史一次消融实验中，完整检索配置为 98.0%。这些数字属于对应历史代码版本和实验配置的结果，不能直接视为 AgentArts 改造版本的性能。

## 五、基于 AgentArts 的核心设计

### 5.1 智能体工作流

系统拟构建一条可观察、可测试的主工作流。

**步骤一：接收并解析游客需求。**

将自然语言转换为结构化场景状态，包括当前位置、剩余时间、同行人员、行动能力、必去景点、偏好和返程要求等。

**步骤二：判断信息完整性。**

对必要字段和关键约束进行检查。若缺少会影响决策的重要信息，则通过平台支持的提问或条件分支机制请求补充，而不是任意填充缺失值。

**步骤三：获取事实证据。**

调用现有知识检索服务，返回相关资料、来源标识和检索记录。对于缺乏可靠依据的内容，应提示信息不足。

**步骤四：调用路线规划工具。**

将结构化需求传递给现有路线规划接口，生成候选路线及时间安排。

**步骤五：执行独立约束校验。**

检查路线连通性、总时间、景点停留时间、行动能力限制及已登记的演出时间窗。校验器不依赖大语言模型对路线正确性的自我判断。

**步骤六：处理不可行请求。**

当路线违反硬约束时，系统不得将其标记为可行。应尝试减少非必要偏好、调整游览顺序或缩减景点；若仍不可行，则明确拒绝并说明原因。

**步骤七：生成最终答复。**

整合已验证的路线、时间预算、证据来源、满足条件、未满足条件和必要提示。

**步骤八：记录执行过程。**

记录输入摘要、工作流分支、工具调用、验证结果、异常和最终输出，用于故障定位及后续评测。

### 5.2 工具接口设计

为降低平台集成难度，第一阶段优先通过 AgentArts 工作流的 HTTP 请求节点调用现有服务；当需要更标准化的工具发现、复用和协议接入时，再评估将工具封装为 MCP 服务。

建议定义以下逻辑工具：

| 工具 | 输入 | 输出 |
|---|---|---|
| `extract_scene_state` | 游客自然语言需求 | 结构化场景状态、缺失字段及置信信息 |
| `search_knowledge` | 查询文本、检索条件 | 候选证据、来源和检索记录 |
| `plan_route` | 场景状态、路网约束 | 候选路线、时间安排和规划状态 |
| `validate_route` | 候选路线、场景状态 | 可行性、硬约束违规项和原因 |
| `suggest_alternative` | 原始需求、失败原因 | 调整后的候选方案 |

以上为逻辑接口设计，具体名称、参数和返回字段将在接口审计后确定，不代表这些工具目前已经完成 AgentArts 注册。

### 5.3 异常处理机制

针对工具调用失败、模型服务异常、检索无结果、信息不足和路线不可行等情况，分别设置明确的错误分支。

- 检索失败：说明证据获取失败，不伪造来源。
- 路线规划失败：返回可解释的失败状态，不输出未经验证的可行路线。
- 校验失败：拦截结果并记录违规原因。
- 模型超时：在安全边界内重试或降级至确定性能力。
- 信息缺失：优先追问关键条件。
- 多项约束冲突：解释冲突项，并给出经过重新验证的替代方案。

AgentArts 的 HTTP 请求节点存在请求时限和接口能力限制，具体工作流需要按照平台当前文档配置。涉及较长执行链的任务应拆分节点，并明确设置超时、异常处理和重试策略。

## 六、项目创新点

### 6.1 智能体编排与确定性决策相结合

传统大语言模型应用容易将需求理解、路线生成和结果判断集中在同一个生成环节。本项目将智能体编排与确定性规划分离：智能体负责理解、组织和调用，规划器负责计算，校验器负责判断是否满足硬约束。

创新重点是针对复杂文旅决策场景形成可复核的系统架构，而非宣称发明了新的大语言模型或全新的图搜索算法。

### 6.2 从答案生成转向约束驱动的任务完成

系统不仅评价答复是否流畅，还检查最终方案是否满足时间、连通性、行动能力和其他必要条件。

当用户目标不可同时满足时，系统明确指出冲突，并在约束允许的范围内提出替代方案。

### 6.3 决策证据链与独立校验

将知识来源、工具调用、路线计算、约束验证和最终答复关联起来，便于定位错误发生在需求解析、事实检索还是规划环节。

### 6.4 面向失败场景的可信降级

针对模型不稳定、资料缺失和服务异常，建立可观察的异常分支与明确的拒绝机制，降低系统因追求完整回答而输出不可靠建议的风险。

上述创新点均为拟通过工程实现和对照实验验证的设计目标，不预先宣称已经达到特定性能提升。

## 七、实验设计与验收指标

### 7.1 测试集设计

拟建立 80 个端到端测试案例：

| 测试类别 | 案例数量 | 测试重点 |
|---|---:|---|
| 景区事实问答 | 20 | 答案正确性、证据覆盖和来源一致性 |
| 可行路线规划 | 20 | 路线连通性、时间预算和硬约束满足情况 |
| 不可行请求 | 15 | 违规拦截、拒绝正确性和替代方案 |
| 信息缺失与主动追问 | 15 | 关键字段识别和澄清准确性 |
| 工具异常与边界情况 | 10 | 超时、无结果、错误返回和降级行为 |
| 合计 | 80 | 端到端系统评测 |

测试集应在正式评测前冻结，记录案例定义、输入、预期结果和版本信息。开发阶段使用的案例与独立盲测案例应尽可能分离，避免只对已知样本进行优化。

### 7.2 对比实验

至少比较以下系统：

1. 原版灵小禅：现有系统基线。
2. AgentArts 改造版：完成真实平台集成后的系统。
3. AgentArts 关闭独立校验的消融版本：用于分析约束校验对结果可靠性的影响。

在相同数据、相同测试条件和可比模型配置下，记录各版本表现。若模型或平台调用配置无法完全一致，应明确记录差异，不将其解释为单一模块的因果贡献。

### 7.3 主要指标

| 指标 | 统计方式 | 初始验收目标 |
|---|---|---|
| 事实问答通过率 | 通过事实契约检查的案例比例 | 目标不低于 90%，以冻结测试集实测为准 |
| 路线硬约束违规数 | 最终被系统标记为可行的路线中，违反硬约束的数量 | 固定测试集上为 0 |
| 不可行请求处理正确率 | 正确识别并处理不可行请求的比例 | 目标不低于 90% |
| 关键缺失字段识别率 | 正确识别应追问字段的案例比例 | 目标不低于 90% |
| 工具调用成功率 | 成功完成规定工具调用的比例 | 目标不低于 95% |
| 端到端响应时间 | 记录平均值、P95 和超时率 | 先建立基线，再根据实际运行确定目标 |
| 结果可审计率 | 能够关联输入、工具结果、校验记录和最终输出的案例比例 | 目标为 100% |

以上均为计划验收目标，并非当前系统的已测成绩。若初测未达到，应保留失败数据、分析原因并进行迭代，不通过修改统计口径掩盖失败。

### 7.4 实验复现要求

每次正式实验至少保存：

- 代码提交版本及工作区状态。
- 测试集版本和数据哈希。
- 模型名称、服务商实际返回的模型身份及关键参数。
- 工作流版本、工具接口版本和运行配置。
- 原始输出、执行 Trace、失败样本和质量门禁结果。

只有在上述条件可核对的情况下，才将对应结果纳入正式申报材料。

## 九、团队分工

团队按三名学生和一名指导教师的模式组织，具体人员以正式报名信息为准。

**项目负责人：** 负责整体架构、核心技术决策、项目进度、质量门禁和答辩。

**平台与后端开发：** 负责 AgentArts 工作流、工具接口、部署环境、认证及异常处理。

**评测与材料负责人：** 负责测试集、对照实验、失败样本、实验报告、演示视频和答辩材料。

**指导教师：** 负责技术路线审查、创新性把关、参赛合规性和阶段成果指导。

所有成员应理解系统关键技术和测试结果，不能只依赖自动生成的材料进行答辩。

## 十、项目风险及应对措施

### 10.1 既有 AIC 获奖作品的资格风险

本项目此前已在 AIC 中获奖。公开赛事通知要求不得将其他赛事作品在不加改进的情况下直接参赛，但不能据此推断所有曾获奖作品都被禁止。

应对措施：提交获奖版本、代码差异计划和新版本设计，向赛事组织方取得明确的资格意见；若确认不符合要求，及时切换到完成独立资格核查的备用项目。

### 10.2 AgentArts 集成风险

平台接入可能受到权限、网络可达性、API 认证、请求时限和资源配额影响。

应对措施：先实现最小工作流和单工具调用，再扩展完整流程；核心后端服务部署在安全、稳定且平台能够访问的 HTTPS 环境中，不直接暴露个人电脑或本地开发端口。

### 10.3 数据真实性风险

部分道路、步行时间和设施信息仍需现场或权威资料核验。

应对措施：维护数据来源、核验时间和估算标记；不将未核验信息表述为实测结果，不将静态路网结果描述为实时导航保证。

### 10.4 评测证据风险

历史基线不等于改造版性能，单次实验也不足以证明模块普遍有效。

应对措施：冻结独立测试集，保留模型身份和运行配置，使用统一统计口径进行对照实验，并披露未达到目标的结果。

### 10.5 进度风险

备赛周期较短，平台迁移、真实数据验证和材料准备可能相互挤占时间。

应对措施：优先保障资格确认和核心闭环，数字人、语音、图片识别等附加功能仅在核心系统稳定后考虑，不以增加功能数量替代可靠性验证。

## 十一、预期成果

项目计划形成以下交付物：

1. 基于 AgentArts 的可运行智能体工作流。
2. 具备知识检索、路线规划、独立约束校验和异常处理能力的业务系统。
3. 标准化工具接口及完整部署说明。
4. 独立测试集、评测脚本、对照实验报告和原始执行证据。
5. 可复现的演示环境、演示视频和答辩 PPT。
6. 完整的代码版本、依赖配置、提交清单和复现指南。
7. 既有获奖版本与华为 ICT 参赛版本之间的技术演进记录。

最终成果以实际完成和通过验收的内容为准，不将尚未实现的功能列为已交付成果。

## 十二、总结

本项目拟以灵山 AI 导览为工程基础，以华为 AgentArts 为智能体编排平台，针对景区导览中的复杂需求理解、事实可靠性、路线可行性和异常处理问题，构建可信文旅决策智能体。

项目的核心设计原则是：由智能体完成任务编排，由专业工具执行检索和规划，由独立校验器判断结果是否满足硬约束，并通过可审计的执行记录和独立对照实验验证系统质量。

与单纯的景区问答机器人相比，本项目更强调复杂任务的实际完成、结果可信性和工程可复现性。

本方案为参赛设计稿。AgentArts 集成、改造后的性能提升、真实游客验证及参赛资格均需按计划完成核验后，方可在正式申报材料中作为已验证成果进行陈述。
